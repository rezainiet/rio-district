# Meta checkout tracking: implementation and live verification

## Project contract

The catalog has six Brazil-jacket color variants. The hosted payment contract accepts one jacket for **EUR 19.99** or one two-jacket bundle for **EUR 24.95**, with zero shipping. The server recomputes prices from the catalog and rejects other carts or currencies before creating a hosted order. The two approved tracking destinations are `https://www.molipy8trk.com/2J23GL9/TTF23GH/` (single) and `https://www.molipy8trk.com/2J23GL9/TRSKRX3/` (bundle). Checkout navigation is in the **same tab**. Product “Acheter maintenant”, cart drawer “Commander”, and cart page “Commander” lead to `/commande`; the final “Continuer vers le paiement” button requests a server-built redirect. “Reprendre le paiement” reuses the pending order and attempt.

## Events and consent

- The storefront initializes project Meta Pixel `1378153049835069` only after the visitor accepts its marketing cookie choice. Eligible storefront routes queue `PageView`; a product route also queues `ViewContent` with product ID, displayed price and EUR. Private confirmation and local test routes do not queue page events.
- A valid `/commande` visit sends one Meta `InitiateCheckout` per cart in the current tab after marketing consent and a successful server quote. It includes product IDs, quantities, item count, and the server-confirmed EUR amount. Accepting consent on the checkout page also triggers it once. Invalid, empty, or unavailable checkouts do not send it. A valid live checkout submission or payment resumption queues one Snapchat `START_CHECKOUT` per order; it does not send another Meta checkout event. Neither browser pixel sends `Purchase` from this website.
- A valid `fbclid` from a landing URL is retained for the current tab only after marketing cookie consent. It is sent to the order API only when the separate, unchecked partner-tracking checkbox is also selected. The server stores it on the pending hosted order so a retry keeps the same value, and adds it as `fbclid` to the Everflow tracking link. A later ad landing with a new click ID replaces the tab's previous one. Refusal or unavailable storage prevents capture/transport. A visitor who leaves the landing page before granting cookie consent may lose the click ID; this is an intentional consent boundary.
- `sub5` carries the configured Meta pixel ID only with the partner checkbox. Existing configured `source_id` and `sub1` values are preserved. They are project-level, server-side configuration; no unverified provider `key` parameter has been invented. A secret API credential must never be appended to a customer URL.
- Browser Meta events contain no customer name, email, phone, address, `fbclid`, or order token. The provider redirect contains customer prefill fields (`sub10`, `adv3`, `sub3`, `sub4`, `sub6`, `sub7`, `sub8`) and product metadata (`adv1`, `adv2`). These are URL-encoded, never stored as one URL, and never logged by the application. They are nevertheless visible to the tracking provider and in browser/network history. The exact required fields and the provider's use of them still need account-level confirmation.

[Everflow's parameter guide](https://helpdesk.everflow.io/customer/your-guide-to-parameters-macros) documents `fbclid` on Partner Tracking Links and `source_id`/`sub1` as separate fields. [Everflow's Meta integration guide](https://helpdesk.everflow.io/customer/meta-facebook-instagram-integration) describes `fb.1.{timestamp}.{fbclid}` for CAPI `fbc` and automatic hashing of personal-data macros, but this project's actual partner postback configuration and field visibility have not been inspected. Do not infer that the provider is sending Purchase or limiting customer data correctly from the URL alone.

## Local checks completed

- Unit tests cover both exact offer URLs, EUR prices, customer URL encoding, consented `sub5`, sample `fbclid` transport, preservation of `sub1` and `source_id`, the consented one-time Meta checkout event, and the absence of browser Meta/Snap Purchase events on checkout click.
- The isolated MongoDB API test covers order persistence of the sample `fbclid`, omission without partner consent, idempotent retries, pending payment state, and rejection of unsigned Everflow webhooks (`501`).
- The local browser simulator covers single and bundle flows at 390px and 1440px, cart drawer, cart page, product “Buy now”, final checkout, and payment resumption. The local simulator never visits the external tracking domain or charges a card. Browser QA also checks that accepted consent queues `PageView`/`ViewContent` and one `InitiateCheckout` on a valid checkout, that refusal queues none, and that the sample `fbclid` survives client-side navigation.

Keep any secret credential server-side. Confirm the partner-required customer-prefill fields, allowed country, final payment domain, product/variant handoff, and actual EUR amounts charged.
2. Inspect the actual Everflow partner postback/CAPI mapping: event name, conversion status filter, Pixel ID, `fbclid`/`fbc` mapping, customer fields exposed to the Meta partner, hashing, value source, and currency source. Restrict partner visibility to fields actually required. Verify that declined, abandoned, refunded, and replayed conversions do not produce a new Purchase.
3. With a genuine Meta ad click, verify the original `fbclid` in the landing URL, stored consent state, outbound checkout URL, and Everflow click/conversion report. The sample ID proves transport only, not attribution.
4. Complete one controlled successful payment. Match the provider transaction to the local order, charged amount and **EUR** currency. Check the Everflow postback report and Meta Events Manager for exactly one Purchase with the same value/currency. Repeat the provider notification and test a declined/abandoned payment. If browser and server Purchase are ever both enabled, use matching browser `eventID` and server `event_id` for that transaction; the current website sends no Purchase and has no active CAPI sender.

The Everflow webhook adapter is intentionally unavailable until a signed payment-confirmation contract exists. Local pending orders, checkout redirects, and return pages cannot mark an order paid or establish Purchase attribution.
